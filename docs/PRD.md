## 1. 背景

日常的截图、OCR、翻译分散在几个工具里（截图软件、Umi-OCR、翻译软件），切换成本高；OCR 结果还要手动清理空格、标点、断行；翻译默认走云端。

snapocr 是一个**独立运行**、托盘常驻的 GUI 小工具：**一个热键完成一件事，结果直接进剪贴板**。OCR 引擎内置在 snapocr 里（RapidOCR，PP-OCR 模型），翻译用本机本地模型。装好 snapocr 后，不再需要 Umi-OCR。

## 2. 目标与非目标

**目标**
- G1：全局热键分别完成"截图 → 剪贴板""截图 → OCR 文本 → 剪贴板""截图 → 译文 → 剪贴板"。
- G2：只运行 snapocr 一个软件（翻译时另需本地模型服务）；全程本地离线。
- G3：后处理规则、翻译模型、热键可配置；核心逻辑可在无 GUI 环境下测试。

**非目标（本阶段不做）**
- 不自研 OCR 模型（使用 PP-OCR 现成模型）。
- 不 fork 或修改 Umi-OCR 源码。
- 不做录屏、长截图。（截图标注、贴图 v0.8 起移入范围，见 F14、F15。）
- 默认不调用云端大模型；以后若要接云端，必须显式开启。
- 只支持 Windows 11，不做跨平台。（v1.8：M9 计划支持 macOS，细节另定。）
- 不做安装包 / 打包分发（先用 venv 启动）。

## 4. 产品形态与交互

- 启动后只在系统托盘常驻，没有主窗口。托盘菜单：截图 / OCR / 截图翻译 / 文字翻译 / 代码 OCR / 表格 OCR（与热键等价）、设置…、退出。设置窗口里有“高级设置（打开配置文件）”。
- 默认热键（两键组合，可在设置窗口或配置文件里改）：

  | 热键 | 动作 |
  |---|---|
  | `Alt+1` | 截图 → 剪贴板 |
  | `Alt+2` | 截图 OCR → 剪贴板 |
  | `Alt+3` | 截图翻译 → 翻译窗口 + 剪贴板（F19） |
  | `Alt+4` | 打开翻译窗口，手动输入文字翻译（F19，v1.3 起；原来是“上次结果”） |
  | `Alt+5` | 截图代码 OCR → 保留缩进的代码文本 → 剪贴板（F13） |
  | `Alt+6` | 截图表格 OCR → 表格 → 剪贴板（F16） |

- 按下截图类热键 → 冻结当前所有屏幕 → 框选区域 → 松开鼠标后可拖动控制点调整大小、拖动选区移动位置 → Enter 或双击选区确认后执行对应动作（F6-5）。Esc 或右键取消。截图动作（`Alt+1`）在选区旁多一条标注工具栏，可以画框、箭头、写字后再复制，或钉在屏幕上，或另存为图片文件（F14、F15、F17）。
- 截图和 OCR 的结果用托盘通知提示；翻译结果用翻译窗口显示（F19）。

## 5. 架构概览

```
GUI 外壳 (snapocr.gui, PySide6) ── 托盘 / 热键 / 框选遮罩 / 翻译窗口 / 剪贴板
        │ 只做界面和 I/O，不含业务规则
        ▼
动作编排 (snapocr.actions) ── capture / ocr / translate 等流程
        │
        ├── OCR 引擎适配层 (snapocr.engines)   → RapidOCR（进程内，onnxruntime，本地模型文件）
        ├── 文本后处理 (snapocr.postprocess)    纯逻辑：版面整理、空格、标点、段落
        └── 翻译适配层 (snapocr.translators)    → 本地模型 OpenAI 兼容接口（默认 Ollama 127.0.0.1:11434）
```

**新增运行时依赖及理由**
- `rapidocr` + `onnxruntime`：内置 OCR 引擎。使用 PaddleOCR 的 PP-OCR 模型（与 Umi-OCR 同一模型家族，中英混排效果好），Apache-2.0，pip 即装，支持 Python 3.12，在进程内调用，不需要外部 exe 或服务。
- `PySide6`：一个依赖同时覆盖托盘、多屏高 DPI 框选遮罩、剪贴板图片、浮窗，是 Qt 官方 LGPL 绑定。代价是体积大（约 200 MB，只装在 venv 里）。
- 全局热键用 Win32 `RegisterHotKey`（`ctypes`，标准库），不引入第三方热键库。
- 屏幕截取用 Win32 GDI（`BitBlt` 进 `CreateDIBSection`，`ctypes`；2026-10-27 M3 WI-8 起，原为 `BitBlt` + `GetDIBits`）一次截下整个虚拟桌面的物理像素，不用 `QScreen.grabWindow`（混合 DPI 多屏下坐标不可靠），不引入 mss / Pillow。单实例用 Win32 命名互斥量（`CreateMutexW`，`ctypes`）。（2026-10-26，M2 计划 D4、D5）
- 翻译窗口的毛玻璃（F20，v1.6）用 `user32.SetWindowCompositionAttribute`（`ACCENT_ENABLE_ACRYLICBLURBEHIND`，`ctypes`），圆角用 `DwmSetWindowAttribute`（`DWMWA_WINDOW_CORNER_PREFERENCE`），不引入第三方库。不用文档化的 `DWMWA_SYSTEMBACKDROP_TYPE`：2026-10-28 实测，Qt 的透明无边框窗口是 layered window，DWM 只画出灰色后备色，没有透底效果；`SetWindowCompositionAttribute` 没有公开文档，Windows 更新后可能失效，失效时按 F20-4 改用实底。
- HTTP（翻译）用标准库 `http.client`，不引入 requests/httpx。不用 `urllib.request`：它会读取系统代理（环境变量、Windows 注册表）并自动跟随 3xx 跳转，可能把请求带出 127.0.0.1（2026-10-25 定，F4 D3）。

**翻译模型服务**：snapocr 不内置大模型推理，通过 OpenAI 兼容接口调用本机的 Ollama（或 LM Studio、llama.cpp server，改配置即可）。原因是 7B 模型的 GPU 推理放在独立服务里更稳，也能与其他工具共用。

## 7. 功能需求与验收标准

验收标准写成可测试的形式，是 TDD 计划的直接输入。

### F1 OCR 引擎（M1）

| ID | 验收标准 |
|---|---|
| F1-1 | 给定图片字节（PNG），返回引擎无关的结构化结果：文本块列表（文本、四点坐标、置信度）。业务代码只依赖这个结构，不依赖 RapidOCR 的类型。 |
| F1-2 | 图中无文字时返回空结果，不报错。 |
| F1-3 | 输入为空、不是图片或图片损坏时，抛出明确异常，信息说明原因。 |
| F1-4 | 运行时不联网：模型文件在本地；模型缺失或加载失败时抛出明确异常，给出模型路径和修复方法。 |
| F1-5 | 引擎首次使用时加载，之后复用同一实例；加载失败不会让程序崩溃。 |
| F1-6 | 最低置信度可配置（默认 0.5【待确认】），低于阈值的块被过滤。 |
| F1-7 | 对固定的样例图片（`tests/fixtures/`，中文、英文、中英混排各一张），识别文本与人工校对文本一致（允许的字符错误率在计划中确定）。 |

### F2 文本后处理（M1）

| ID | 验收标准 |
|---|---|
| F2-0 | 版面整理：按坐标把文本块排成阅读顺序（从上到下、从左到右），同一行的块合并成一行；行间竖直间隔明显大于正常行距时（初值 1.5 倍行高中位数）标记为段落间隔。阈值是计划内常数，由 F2 计划 WI-8 用样例图校准。 |
| F2-1 | 中文与英文 / 数字之间补一个半角空格（"使用Python3" → "使用 Python3"）。 |
| F2-2 | 中文语境下的半角标点转全角（`,` → `，`），英文句子、URL、代码、数字里的标点不变。 |
| F2-3 | 把被 OCR 断开的同一段落的行合并；空行和列表项保持分段。合并条件（2026-10-25 定，方案 B）：相邻两行**同时满足**——两行之间没有段落间隔、上一行不以句末标点结尾、上一行是满行（右边缘达到区域宽度的约 0.85 倍）、下一行不是列表项。默认开启，可关闭；误合并时在翻译窗口里改（截图翻译）或关掉这条规则。 |
| F2-4 | 每条规则可单独开关；规则链的顺序固定，并有文档说明。 |
| F2-5 | 性质：所有文本规则**幂等**（处理两次 = 处理一次）；空字符串输入输出为空字符串。 |

## 8. 非功能需求

| 项 | 要求 |
|---|---|
| 离线 | 只访问 `127.0.0.1`（本地模型服务），不发起任何外网请求；OCR 模型文件在本地。<br>**保证范围**（2026-10-26，F4 审查 C1）：只覆盖 snapocr 自己发起的连接。127.0.0.1 上的服务若再把请求转出本机（LiteLLM 等路由、配置了远程上游的代理），snapocr 无从判断，由使用者保证 `base_url` 指向真正的本地模型服务。Ollama 云模型在配置阶段按模型名拒绝（F4-6）。 |
| 延迟 | 热键到遮罩出现 < 300 ms；OCR 从确认选区到剪贴板就绪 < 2 s（引擎已加载，1080p 满屏密排文字，CPU；原目标 1.5 s，2026-10-25 按实测由 Jeremy 改为 2 s，M2 用真实截图复测）；翻译 200 字以内 < 3 s（热态：模型已加载，RTX 5080）；冷启动（模型被 Ollama 卸载后的第一次翻译）< 20 s，期间浮窗显示“翻译中”（F8-2）。原目标 5 s，2026-10-26 按实测由 Jeremy 改为热态 3 s / 冷启动 20 s；冷启动不做自动化测试（需要先让 Ollama 卸载模型，不稳定），只按 §10 记录实测。<br>**实测（2026-10-25，WI-10）**：Intel Core Ultra 9 285K（24 核），onnxruntime 1.31.0 CPU，默认线程设置；1920×1080 密排 12 行中英文，加载 0.46 s，首次 2.54 s，预热后 5 次中位数 1.76 s（1.70–1.85 s），未达原 1.5 s 目标，满足新目标 2 s。<br>**翻译实测（2026-10-26，F4 WI-9）**：Ollama 0.40.11，hy-mt2:7b（Q6_K），RTX 5080；164 字中文段落译英文，模型已加载，预热后 5 次中位数 1.22 s（1.21–1.23 s），满足 3 s 目标。冷启动见 §10。<br>**M2 实测（2026-10-26，WI-23，`tests/perf/test_gui_latency.py`）**：双屏 3840×2160 @200% + 3440×1440 @150%；热键（`SendInput` 注入）到所有遮罩出现，7 次中位数 261–276 ms（3 轮），满足 300 ms，但余量小，其中一次整屏截取约 150 ms；**启动后第一次按热键约 540–620 ms**（截取和遮罩窗口第一次创建）。真实截图 1920×1080 密排 12 行，从按 Enter 确认选区到剪贴板就绪，5 次中位数 1.37–1.39 s，满足 2 s。<br>**M3 WI-8 复测（2026-10-27，截取改用 DIB section）**：整屏截取约 120 ms（原约 155 ms）；热键到所有遮罩出现，7 次中位数 205–212 ms（3 轮）。拆分后，“启动后第一次约 550 ms”只出现在启动后约 2 s 内（和引擎预热抢 CPU）；预热完成后第一次 267–274 ms（多出的约 80 ms 是窗口第一次激活），之后约 190 ms。 |

## 10. 风险

| 风险 | 应对 |
|---|---|
| RapidOCR 首次运行需要下载模型，违反离线要求 | 安装时一次性准备好模型文件，运行时只读本地路径；F1-4 用测试钉住"不联网" |
| RapidOCR 识别效果不如 Umi 现在的效果 | F1-7 样例对比 + 评测集；适配层隔离，可换 PaddleOCR 或 VLM |
| 标点 / 空格规则误伤代码和 URL | 用性质测试和反例覆盖；S4 代码模式单独处理 |
| 多屏不同缩放下截图错位 | 坐标换算抽成纯逻辑并重点测试；真实多屏组合手工验收 |
| `Alt+数字` 与其他软件冲突 | 可配置 + 注册失败明确通知（F5-3） |
| HY-MT2 在 Ollama 中无法加载（架构 `hunyuan-dense`、模板需手写） | 先实测导入；不行就改用 LM Studio 或 llama.cpp server，接口相同，只改配置 |
| 本地模型首次加载慢（实测 hy-mt2:7b 冷启动 14.7 s，已加载后单句 0.2–0.3 s，显存约 10 GB） | 超时可配置；冷启动期间浮窗显示“翻译中”；模型可换。M2 不做启动预热、也不带 `keep_alive`（2026-10-26，M2 计划 D13：每次启动都把模型拉进显存代价大，翻译不一定会用；OpenAI 兼容接口也不一定支持 `keep_alive`），放到以后 |
| 毛玻璃用的是没有公开文档的 `SetWindowCompositionAttribute`（F20） | 只在 `snapocr.gui.platform` 的薄封装里调用；调用失败或系统条件不满足时改用实底（F20-4），功能不受影响 |
| 范围膨胀 | 严格按里程碑做，M1 验收完再开 M2 |
